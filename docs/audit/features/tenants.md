## Open gaps

The rows below are the findings of the depth pass of 2026-10-21 that the rebuild could not close,
because the gap sits in the API, in the model or in the shared types. The rows the rebuild closed are
recorded in the Closed section below with their date; their ids are the ones of the depth pass
(docs/audit/features/tenants_audit_pass1_20260908-230000.md).

| ID       | Severity | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                              | Path                              |
| -------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| TEN-D3-1 | P2       | The tenant model holds no lease end date: moveInDate and moveOutDate are the only dates of a stay (apps/api/src/models/tenant.ts:8-9, :84-91). A stay that is about to end therefore cannot be computed from the server's numbers, and the roster can only show how long a resident has been here. A lease end field on the model, written by the office, would close it. The screen: apps/web/src/app/(admin)/tenants/page.tsx.                 | apps/api/src/models/tenant.ts     |
| TEN-D3-2 | P2       | GET /tenants has no money filter and no dues aggregate (apps/api/src/routes/tenants.ts:391-483): the roster reads GET /tenants/:id/dues for every resident on the page, so the "Owing money" number covers the page and not the whole set, and the office cannot ask the server for "the residents who owe money". A dues aggregate on the list route, or a filter on it, would close it. The screen: apps/web/src/app/(admin)/tenants/page.tsx. | apps/api/src/routes/tenants.ts    |
| TEN-D3-3 | P2       | The tenant model has no status field, so the domain carries no lifecycle vocabulary (packages/types/src/lifecycle.json) and the admin panel cannot render the shared stepper. The onboarding trail on the resident page is drawn from the fields the record holds, and the portal has no tenant vocabulary of its own. The model: apps/api/src/models/tenant.ts.                                                                                 | packages/types/src/lifecycle.json |
| TEN-D3-4 | P2       | A check out deactivates the portal login of the resident and of the guardians (apps/api/src/routes/tenants.ts:820-843) and sends no notification, so the resident is never told that the stay ended and cannot be reached to ask about it. The office page says so before the write, but the resident is still in the dark. The screen: apps/web/src/app/(admin)/tenants/[id]/page.tsx.                                                          | apps/api/src/routes/tenants.ts    |
| TEN-D3-5 | P3       | PUT /tenants/:id writes an audit entry only when the room or the bed moved (action tenant_transfer, apps/api/src/routes/tenants.ts:681-702). A change of the rent or of the phone leaves no trail at all, so the office cannot show what a resident was told they owe. The screen: apps/web/src/app/(admin)/tenants/[id]/edit/page.tsx.                                                                                                          | apps/api/src/routes/tenants.ts    |
| TEN-D3-6 | P3       | The resident record carries no link back to the enquiry it came from: the server stores convertedTenantId on the enquiry (apps/api/src/routes/tenants.ts:313-323), not the other way round, and the enquiry has no reverse read. The resident page can only point at the converted enquiries list. The screen: apps/web/src/app/(admin)/tenants/[id]/page.tsx.                                                                                   | apps/api/src/routes/enquiries.ts  |
| TEN-D3-7 | P3       | The shared tenant DTOs of packages/types/src/tenant.ts have no importer: the API uses its own model interface and the four admin screens declare their own interfaces, so a page shape can drift from the API contract. The screens: apps/web/src/app/(admin)/tenants.                                                                                                                                                                           | packages/types/src/tenant.ts      |
| TEN-D3-8 | P3       | The KYC queue has no list of its own. A resident who uploads a document waits for a verdict and the only queue is the notification bell (apps/api/src/routes/tenants.ts:1097-1131), and the roster cannot filter by the identity state because GET /tenants does not filter on it. The screen: apps/web/src/app/(admin)/tenants/page.tsx.                                                                                                        | apps/api/src/routes/tenants.ts    |

## Closed

| Claim                                                                                                                                                      | Live proof                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TEN-D2-1 - the roster had no money column, so the office could not see who owes money from the list                                                        | CLOSED 2026-10-21 - the "Owes now" column reads GET /tenants/:id/dues for every resident in view and shows the server's total, the open invoice count and the per invoice remaining balance; a closed stay carries no open invoice and a balance the server did not report is never read as zero |
| TEN-D2-2 - the roster said nothing about what the identity state of a resident meant                                                                       | CLOSED 2026-10-21 - the identity column names the state (Verified, Waiting, Incomplete, None) and says what is missing, read from the document record the server holds                                                                                                                           |
| TEN-D2-3 - the list did not say what its columns meant                                                                                                     | CLOSED 2026-10-21 - the legend under the table names the scope of the search (the resident name only), of the dues column, of the stay and of the rent and the deposit                                                                                                                           |
| TEN-D2-4 - the CSV export carried only the page in view and never said so                                                                                  | CLOSED 2026-10-21 - the export walks the pages of the filtered set and reports the rows the server holds against the rows the file carries                                                                                                                                                       |
| TEN-D2-5 - the resident page never showed what the resident owes unless the office opened the checkout modal                                               | CLOSED 2026-10-21 - the dues summary is read on the page itself and rendered as the money number of the record and as the resident's own view, beside the link to the office ledger                                                                                                              |
| TEN-D2-6 - the onboarding of a resident was scattered over four cards and no progression was drawn                                                         | CLOSED 2026-10-21 - the onboarding trail renders the progression the record proves: the account, the move-in, the two documents, the verification and the move out                                                                                                                               |
| TEN-D2-7 - the office could only delete a resident from the roster, and several actions were unreachable from the resident page                            | CLOSED 2026-10-21 - every office action is on one card of the resident page (WhatsApp, copy, statement, police form, check out, reinstate, delete) and each write renders the server's answer                                                                                                    |
| TEN-D2-8 - the check out and the reinstate reloaded the whole page with window.location.reload(), which threw the view away and claimed the result locally | CLOSED 2026-10-21 - both writes invalidate the record, its dues, its payments, its invoices and its activity, and the page reports the state the server committed                                                                                                                                |
| TEN-D2-9 - the edit page did not say that an edit moves what the resident owes, nor that the resident is told                                              | CLOSED 2026-10-21 - the panel on the edit page names the four consequences: the rent moves the next invoice, the deposit is not a payment, the contacts are what the resident reads, and no notification and no audit entry reach the resident                                                   |
| TEN-D2-10 - the create page did not say what creating the tenant does, and nothing stopped an unreachable resident                                         | CLOSED 2026-10-21 - the rail panel names what the server commits (the portal account with a one time password, the bed taken, no bill raised, the source enquiry converted) and what is still open, and the phone field carries the reachability rule                                            |
| TEN-D2-11 - the edit page was the only screen of the module outside the shared query stack                                                                 | CLOSED 2026-10-21 - the record is read with useApiQuery, the form is filled from it once, and the write invalidates the tenant queries so the record, its dues and the roster are re-read                                                                                                        |
| TEN-D2-12 - the resident page opened with four statistic tiles and no protagonist                                                                          | CLOSED 2026-10-21 - the four tiles are gone: the page opens with the resident, the bed, the stay and the money number the server reports for that resident                                                                                                                                       |
| TEN-D2-13 - the status filter was a select and the size of the set was never on the screen                                                                 | CLOSED 2026-10-21 - the status lives in a tab strip whose counts are read from the server for the same filtered set the table shows, and the roster, the beds and the owing number sit in the band above them                                                                                    |
