Access rule: admin web = admin only; resident portal = Flutter only; no Next tenant routes
Implementation spec: docs/audit/features/services_audit_pass1_20260908-003801.md
Contract: packages/types/src/contracts/services.ts (state machine, truth contract, layout, next action)

## What this module owns

A service belongs to a FLOOR, not to a room. The model carries a floorId and no room
(apps/api/src/models/serviceStatus.ts:16-19) and the unique index is the floor and the service type
(apps/api/src/models/serviceStatus.ts:66). The residents a service reaches are therefore the
residents of that floor, and the office reads the health of the building floor by floor.

## Acceptance

- [x] API rejects serviceType that is not a per floor amenity definition of AppConfig
      (apps/api/src/routes/services.ts:34-39, :296-303)
- [x] A tenant may only report a service on their own floor, and may never set it to operational
      (apps/api/src/routes/services.ts:372-406)
- [x] A state change pushes a service update to the active residents of the floor, and a floor with
      nobody living on it has nobody to tell (apps/api/src/routes/services.ts:132-190, :442-452)
- [x] The floor, the service and the state of the board live in the address bar, so a view of the
      module is a link (apps/web/src/app/(admin)/services/page.tsx)
- [x] The board shows one tile per floor and service type, names the tiles the server holds no row
      for, and names the floors that carry no row at all
- [x] The edit page writes the state through the path that reaches the residents, and a service type
      change through the path that refuses a duplicate
- [x] The create page says what the save commits and what it refuses, and the bulk run reports the
      answer of the server for every floor

## Open gaps

The rows below are the findings of the depth pass of 2026-10-21 that the rebuild could not close,
because the gap sits in the API, in the model or in the shared types. The rows the rebuild closed are
recorded in the Closed section below with their date; their ids are the ones of the depth pass (the
section at the end of docs/audit/features/services_audit_pass1_20260908-003801.md).

| ID        | Severity | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Path                                 |
| --------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| SVC-D3-1  | P2       | Creating a service row reaches nobody. POST /services writes the row with the state and the note, stamps it with the office and the time and writes a create entry in the audit log, and it sends no notification (apps/api/src/routes/services.ts:279-358). A state of degraded or down written on the create page is therefore never announced to the residents of that floor. The screen says so before the write, and the residents are still in the dark. | apps/api/src/routes/services.ts      |
| SVC-D3-2  | P2       | A service type change reaches nobody and leaves the stamp of the record stale. PUT /services/:id/full writes the new type and an update entry in the audit log, pushes no notification and does not stamp the record with the office and the time (apps/api/src/routes/services.ts:535-567), so the record still carries the office that wrote the row before.                                                                                                 | apps/api/src/routes/services.ts      |
| SVC-D3-3  | P2       | Removing a service row reaches nobody. DELETE /services/:id deletes the row, writes a delete entry in the audit log and broadcasts the change, and it sends no notification (apps/api/src/routes/services.ts:572-597). The floor loses the service and the residents of the floor believe they still have it.                                                                                                                                                  | apps/api/src/routes/services.ts      |
| SVC-D3-4  | P2       | The server cannot filter on a service type. GET /services reads the floor and the state only (apps/api/src/routes/services.ts:215-228), so the board reads the whole set and narrows it on the screen. A filter on the service type on the list route would let the office ask the server for the services of one kind.                                                                                                                                        | apps/api/src/routes/services.ts      |
| SVC-D3-5  | P2       | The list route serves at most 100 rows in one page (apps/api/src/routes/services.ts:231) and there is no endpoint that returns the whole set of the building, so the board walks the pages itself and reports the size of the set it holds.                                                                                                                                                                                                                    | apps/api/src/routes/services.ts      |
| SVC-D3-6  | P2       | The summary route has no consumer. GET /services/summary counts the rows by state over the whole building (apps/api/src/routes/services.ts:200-209) and the board reads the per floor counts of GET /floors/overview instead, so the route is now read by nobody in the admin app or in the portal.                                                                                                                                                            | apps/api/src/routes/services.ts      |
| SVC-D3-7  | P2       | The residents the server tells and the residents the board counts are two different counts. The notification goes to the active tenant records of the floor (apps/api/src/routes/services.ts:141-158) while the board counts the occupied beds the server reports (apps/api/src/routes/floors.ts:151-152). The two differ when a resident record and a bed disagree, and the board names its own count.                                                        | apps/api/src/routes/services.ts      |
| SVC-D3-8  | P3       | The floor of a service cannot be changed and the server has no endpoint that moves a row to another floor. The row is keyed on the floor and the service type (apps/api/src/models/serviceStatus.ts:66), so moving it means removing it and creating it again, and the residents of the floor lose the service in the meantime.                                                                                                                                | apps/api/src/models/serviceStatus.ts |
| SVC-D3-9  | P3       | The history of a service lives only in the audit log. The model holds the state, the note, the office and the time of the last write (apps/api/src/models/serviceStatus.ts:35-49) and nothing else, and the audit entries expire after 90 days (apps/api/src/models/auditLog.ts:82), so a change that reached nobody leaves no trace after a quarter.                                                                                                          | apps/api/src/models/auditLog.ts      |
| SVC-D3-10 | P3       | The shared service DTOs of packages/types/src/service.ts have no importer in the repository: the API uses its own model interface and the four admin screens declare their own interfaces, so a page shape can drift from the API contract.                                                                                                                                                                                                                    | packages/types/src/service.ts        |
| SVC-D3-11 | P3       | The code of a refusal is lost on the create path. The route hands INVALID_SERVICE_TYPE to badRequest, and the helper drops the code it is given (apps/api/src/routes/services.ts:296-303 against apps/api/src/lib/routeUtils.ts:74-76), so the client sees VALIDATION_ERROR and has to read the message to tell a wrong service type from any other refusal.                                                                                                   | apps/api/src/lib/routeUtils.ts       |
