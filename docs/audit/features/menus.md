## Open gaps

The rows below are the findings of the depth pass of 2026-10-21 that the rebuild could not close,
because the gap sits in the API, in the model or in the shared types. The rows the rebuild closed
are recorded in the Closed section below with their date; their ids are the ones of the depth pass
(the section at the end of the pass 1 record).

| ID        | Severity | Gap                                                                                                                                                                                                                                                                                                                                                                                                        | Path                              |
| --------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| MENU-D3-1 | P2       | A menu that changes reaches no resident. No route of the module calls createNotification: the plan is published by being written (apps/api/src/routes/menus.ts:127-166) and the residents read it when the portal pulls GET /menus/today (apps/api/src/routes/menus.ts:43-49). A resident who does not open the app never learns that tomorrow's lunch changed. A notification on the plan would close it. | apps/api/src/routes/menus.ts      |
| MENU-D3-2 | P2       | The server holds no attendance. The model carries the date and the four slots and nothing else (apps/api/src/models/dailyMenu.ts:31-45), so there is no answer to who ate what, and the office cannot close the loop on a dish the residents did not eat. A consumption record per resident per meal would close it.                                                                                       | apps/api/src/models/dailyMenu.ts  |
| MENU-D3-3 | P2       | The whole module sits behind one flag. The router refuses every route of the module with 403 FEATURE_DISABLED when messFeedbackEnabled is off (apps/api/src/routes/menus.ts:14, apps/api/src/middleware/featureFlags.ts:46-62), so with the flag off the office loses the plan and the portal loses the menu, and neither screen says why the other is empty.                                              | apps/api/src/routes/menus.ts      |
| MENU-D3-4 | P3       | The menu model carries no status field, so the domain has no vocabulary in the shared lifecycle (packages/types/src/lifecycle.json) and no stepper can render it. The grid of the module (the plan state of a day times the date) is written out in the contract instead.                                                                                                                                  | packages/types/src/lifecycle.json |
| MENU-D3-5 | P3       | The shared menu DTOs have no importer. packages/types/src/menu.ts declares the day with an id, while the API returns the record with its _id (apps/api/src/routes/menus.ts:113), so the four screens declare their own shapes and a page shape can drift from the API contract.                                                                                                                            | packages/types/src/menu.ts        |
| MENU-D3-6 | P3       | The server cannot filter on a gap. GET /menus reads the date range, the derived active flag and the dish name (apps/api/src/routes/menus.ts:52-99), so the number of the days that still miss a dish is computed on the screen instead of asked of the server. A filter on the empty slots would close it.                                                                                                 | apps/api/src/routes/menus.ts      |
| MENU-D3-7 | P3       | The dish search is bounded. The server clamps a page to 100 rows (apps/api/src/lib/routeUtils.ts:16) and the page asks for the first 50 days that matched, so a dish served on more days than that is not all of them and the page cannot say how many are missing.                                                                                                                                        | apps/api/src/lib/routeUtils.ts    |
| MENU-D3-8 | P3       | The write trail of a day is not permanent evidence: the audit entries expire after 90 days (apps/api/src/models/auditLog.ts:82), so a change that reached nobody leaves no trace after a quarter.                                                                                                                                                                                                          | apps/api/src/models/auditLog.ts   |
| MENU-D3-9 | P3       | The delete of a day has no guard for a past date (apps/api/src/routes/menus.ts:246-279): a day that has already been served can be taken off the plan, and only the delete entry of the audit log remembers that it was there.                                                                                                                                                                             | apps/api/src/routes/menus.ts      |

## Closed

| Claim                                                                                                                                                                                                         | Live proof                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| MENU-D2-1 - the two forms could not be saved at all: the resolver demanded a name on every dish row and the form always carries one empty row per slot, so the submit never ran and the error was never shown | CLOSED 2026-10-21 - the schema of both forms accepts an empty name, the payload drops the empty rows before the write, the error of a row is shown under the row, and the save lands on the day the server wrote         |
| MENU-D2-2 - the filters of the module were local state, so a week of the plan could not be linked, cited or shared                                                                                            | CLOSED 2026-10-21 - the week in view, the days filter and the dish search live in the address bar, so /menus?week=YYYY-MM-DD lands on the same week the sender was looking at                                            |
| MENU-D2-3 - the list showed dates without the food on them, so the office could not see the week it was planning nor the day that was still missing                                                           | CLOSED 2026-10-21 - the week is a grid of days and slots, every cell names the state of its day and the slots that hold no dish, and the missing day links to the form with its date filled in                           |
| MENU-D2-4 - the page had no number of its own and never said what its numbers meant                                                                                                                           | CLOSED 2026-10-21 - the band carries the days in view, the days to plan, the slots to fill and the dishes on the board, every one of them over the days the grid shows, and the legend says what each state means        |
| MENU-D2-5 - a day could only be copied onto another day from inside the shared planner, which read the current week outside the query stack and could not reach another week                                  | CLOSED 2026-10-21 - the day page fills another day with this one: it reads the target day first, says what the copy overwrites, and writes it through the same route the edit page uses                                  |
| MENU-D2-6 - the day page said nothing about who ate and did not link the feedback of that day                                                                                                                 | CLOSED 2026-10-21 - the day page says that the server records no attendance and links the feedback of that day on the meals page, which reads the date out of the address bar                                            |
| MENU-D2-7 - the forms did not say what the save commits, nor that the resident reads the day from GET /menus/today                                                                                            | CLOSED 2026-10-21 - both forms carry the panel that names the write, the audit entry, the refusals of the server and the pull of the portal, and the day page says it as well                                            |
| MENU-D2-8 - the state of a day was drawn from the browser clock, so the badge of a day could disagree with the server                                                                                         | CLOSED 2026-10-21 - the day page takes the past flag from the server's own isActive, and the grid marks a gone day with the reason the server gives for it: a menu for a past date is refused                            |
| MENU-D2-9 - the edit page read the record with a hand written fetch outside the shared query stack and did not re-read it after the write                                                                     | CLOSED 2026-10-21 - the record is read with useApiQuery, the write invalidates the menus queries, and the operator lands on the day re-read from the server                                                              |
| MENU-D2-10 - the empty state said "Create your first daily menu to get started" and nothing about what the residents read                                                                                     | CLOSED 2026-10-21 - the empty state names what the residents see on a day with no menu, and the first day the server still takes                                                                                         |
| MENU-D2-11 - the export wrote the page in view and said nothing about the rest of the set                                                                                                                     | CLOSED 2026-10-21 - the export writes the days of the week in view, the same days the grid shows, and the file carries the dishes of every slot                                                                          |
| MENU-D2-12 - the day page had no write trail, although the audit route can filter by the record                                                                                                               | CLOSED 2026-10-21 - the day page shows the write trail of that day, with the fields the server recorded and the 90 day life of the entries                                                                               |
| MENU-D2-13 - the WhatsApp share did not say what it does and what it leaves behind                                                                                                                            | CLOSED 2026-10-21 - the share stays, and the day page says that it opens a chat with the number of the office, that the server records nothing about it, and that the portal pull is the only delivery the product keeps |
